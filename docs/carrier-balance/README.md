## 2. 调研结论：官方接口到底有没有

这是本次调研的核心问题，结论需要分两层说清楚。

### 2.1 官方接口：存在，但个人拿不到

三家运营商**都**提供官方余额查询接口，位置在各自的能力开放平台，不是没有。但这些接口的获取条件对企业资质有硬性要求：

| 运营商 | 官方接口所在 | 接口 | 余额字段 | 申请条件 |
|---|---|---|---|---|
| 中国移动 | 中国移动 IT 能力开放平台 `it.open.10086.cn` | 「查账户余额」「话费余额鉴权」「查账单」 | 平台文档未在公开页展示字段名 | 企业账号 + 实名认证 + 场景审核，且需用户短信授权码 |
| 中国电信 | 天翼开放平台 `open.e.189.cn` | `POST /api/oauth2/account/queryCTPackage.do` | `totalBalanceAvailable`（单位：**分**） | 企业开发者入驻 + 能力商店申请 + 能力签约 |
| 中国联通 | A-PaaS 能力开放平台 | 「账户余额查询」（API 规范 v1.8 §5.3）、「当月话费查询」§5.6、「欠费查询」§5.4 | 字段名随规范版本 | 企业资质 + 能力申请审核 |
结论：**个人开发者无法自助申请这些接口**。三条硬性门槛——企业实名认证、能力商店申请与资质审核、用户侧逐次短信授权（移动的「用户授权码申请接口」需要用户回短信验证码）。第三点尤其关键：即使拿到接口权限，查询某个用户的话费余额仍需该用户每次授权，这不是能用于后台定时巡检的形态。

因此本项目对个人卡走**网上营业厅页面抓取**，这是个人唯一能拿到程序化数据的路径。

### 2.2 抓取路径的可行性与代价

三家网厅的个人查余额入口（**2026-11-20 实测**）：

| 运营商 | 实测入口 | 实测现象 |
|---|---|---|
| 中国移动 | `https://shop.10086.cn/i/?f=home` | 正常渲染。未登录时跳转 `login.10086.cn/login.html?channelID=12003`，支持扫码登录与短信随机码；首页「服务专区」另有「账单查询」「余量查询」「充话费」直达链接。**已登录实测**：个人中心页显示「我的账户 70.90元交费> 可用余额： 70.90元账单> 账户总余额 ： 0.00元详单>」 |
| 中国电信 | `https://www.189.cn/` | **无头浏览器与桌面浏览器下正文均为 0 字、链接数为 0**，属站点级反爬拦截；`gd.189.cn`、`/service/index.html` 同样为空，`my.189.cn` 连接超时 |
| 中国联通 | `https://www.10010.com/` | 正常渲染（hash 路由 SPA）。首页无余额链接，余额入口在 hover 展开的「查询」二级菜单；页面另有一个 `upay.10010.com/upayWeb/phoneSpeedy` 交费 iframe |

抓取方案的两点现实约束：

1. **省际差异**：网厅是分省部署的，菜单文案与路径在各省不完全一致，所以规则里配了候选关键字组和多个菜单入口文字，按顺序尝试。移动已实测到精确入口，电信与联通仍需实际登录后核对。
2. **电信的反爬是硬约束**：实测无头环境下拿不到任何页面内容，因此电信的抓取**必须依赖桌面 Chrome**（`scripts/start-chrome-debug.cmd` 启动的 CDP 模式，真实浏览器指纹与登录态）。代码已为此加了退路：无头抓取失败时自动改用桌面 Chrome 重试（`allowCdpFallback`），无头上下文也补上了真实 Chrome UA、中文区域与时区。若两者都不可用，电信需退回手动录入。
3. **登录态是前提**：三家都要服务密码或短信验证码，我无法代办，必须由你本人完成一次登录。登录态存在 `src/wallet-states/storage_carrier_*.json`（已在 `.gitignore` 中，不入库）。

### 3.1 两个必须知道的运维约束

**服务要用新代码必须重启。** 服务由 `启动项.bat` 以 `node src/server.js` 启动（无 watch），改了代码不会热重载。运营商查询器是新加的，旧进程里没有，刷新会按通用 API 去请求网厅首页拿到 HTML，报 `Unexpected token '<'`。

**写数据库要走服务，不能直接改文件。** 服务用 sql.js，数据库整个读进内存、每次写操作把全库覆盖写回文件。因此「服务运行中」时直接改 `src/data/llm-manager.db` 会被服务的下一次落盘抹掉（本次就因此丢过电信、联通两条记录）。`scripts/setup-carrier-platforms.mjs` 已改为自动判断：服务在跑就走 HTTP API 写入，服务没跑才直接改文件。

```bash
node scripts/setup-carrier-platforms.mjs            # 三家
node scripts/setup-carrier-platforms.mjs --only cmcc # 只加一家
```

### 3.2 浏览器可执行文件的定位

Playwright 的 `chromium.executablePath()` 依赖 `PLAYWRIGHT_BROWSERS_PATH` 环境变量。登录脚本与巡检服务是两个进程，环境不同：服务由 `启动项.bat` 拉起时不继承该变量，会指向默认 `ms-playwright` 目录——那里通常没装浏览器，报 `Executable doesn't exist`。

代码已改为 `resolveBrowserExecutable()`：按「Playwright 自带 chromium → `PLAYWRIGHT_BROWSERS_PATH` 下的 `chromium-*/chrome-win64/chrome.exe` → 系统安装的 Chrome/Edge」逐个探测**实际存在的文件**，用绝对路径启动，不再依赖环境变量。

### 3.3 189.cn 打不开：两层拦截

**现象**：在自动化浏览器里打开 `https://www.189.cn/`，页面一片空白，正文长度为 0；同一个网址在日常浏览器里正常打开。

这是**两层独立的拦截**，必须都绕过才行。

**第一层：反自动化标记**

| 启动方式 | 结果 |
|---|---|
| 系统 Chrome + 原有启动参数 | 正文 0 字，html 仅 39 字符 |
| 系统 Chrome + 不带任何参数 | 正文 0 字，html 仅 39 字符 |
| 系统 Chrome + `--disable-blink-features=AutomationControlled` | 正文 1186 字，跳转到 `/web/`，出现「账户余额」等业务文案 |

Playwright 默认把 `navigator.webdriver` 置为 `true`，189.cn 据此判定为自动化客户端。修复：`BROWSER_ARGS` 增加 `--disable-blink-features=AutomationControlled`。

**第二层：站点级拦无头浏览器**

第一层修好后，有头模式能打开，**无头模式仍然返回空页面**：

| 模式（均已带登录态） | 结果 |
|---|---|
| 无头 + 拦截图片字体 | 正文 0 字 |
| 无头 + 不拦截图片字体 | 正文 0 字 |
| **有头** | 正文 1257 字，可见「黄** / 190****3361 / 退出登录 / 账户余额」 |

与是否拦截静态资源无关，纯粹由无头模式决定。修复：电信内置规则标记 `headlessBlocked: true`，抓取时改用有头窗口（窗口短暂弹出，抓完自动关闭）。`scrapeWithStorage` 支持 `headless` 参数，`scrapeWalletBalance` 与 `scrapeWalletsBatch` 按该标记分流，避免先无头失败再回退、白等一轮超时。

### 3.4 运营商登录判定：不能只看标签是否出现

189.cn **未登录**的首页文本里就有「账户余额」，只是值为占位符 `--`：

```
中国电信欢迎你 登录 手机 宽带 固话 -- 账户余额 -- 已用通用流量 -- 剩余积分 充值…
```

若登录检测只看「标签是否出现」，会把未登录页面误判成已登录，导出一份无效登录态——表面登录成功，后续巡检却永远抓不到余额。

现用 `detectCarrierLoggedIn()`，满足任一条才算已登录：

1. 页面出现登录后专属文案「退出登录 / 退出」（未登录态实测出现次数为 0）；
2. 余额标签后紧跟真实数字（占位符 `--` 不算；标签与数字之间夹了其他中文标签也不算）。

### 3.5 电信首页是「数值在上、标签在下」

移动网厅是「可用余额： 70.90元」（标签在前），电信网厅相反——金额出现在标签**之前**：

```
…手机 宽带 固话 54 .61 元 账户余额 0 .00 KB 已用专用流量 0 分钟 已用通用语音 0…
```

而且金额被拆成两段渲染（`54` + 换行 + `.61`）。两个后果：

- 沿用「标签后取数」会取不到，或取到下一个栏目（`已用专用流量 0.00KB`）的数值；
- 不做归一化，`54.61` 会被读成 `54`。

修复：内置规则新增 `valueBeforeLabel` 标记，提取时**先**从标签位置往前找紧邻金额，**找不到再**走原来的「标签后跟金额」（兼容其他省份版本的相反布局）；`extractBalance` 先把跨行拆分的小数接回。

相关回归用例在 `scripts/test-carrier-balance.mjs`（60 项）。

## 3.6 登录态能保持多久，以及怎么让它活得久些

### 实测：两家都是「滑动续期」会话

读取登录态文件里的 cookie 过期时间（2026-11-20 实测），并做对照实验（访问一次网厅后对比 cookie 过期时间的变化）：

| 运营商 | 关键 cookie | 登录后过期 | 访问一次后 | 续期窗口 |
|---|---|---|---|---|
| 移动 | `chargeresource` | 登录后 30 分钟 | 推到「访问时刻 + 30 分钟」 | **30 分钟** |
| 移动 | `rdmdmd5` | 30 分钟左右 | 不再下发 | 30 分钟 |
| 电信 | `yiUIIlbdQT3fT` | +7 天 | 推到「访问时刻 + 7 天」 | **7 天** |
| 电信 | `yiUIIlbdQT3fS` | +1 年 | 推到「访问时刻 + 1 年」 | 1 年 |

结论：网厅会话不是固定时长，而是**每次访问都把过期时间往后推**（滑动续期）。只要在窗口内再访问一次，会话就能一直续下去。

### 原来为什么会掉

两个原因叠加：

1. **抓取后从不写回 cookie。** `scrapeWithStorage` 加载 `storageState`、抓完就关浏览器，服务端刷新过的 cookie 全被丢弃。等于每次巡检都在用「登录那一刻」的过期时间重新算起，窗口一过必然失效。实测：14:04 存的移动登录态，15:02 抓取就跳了 `login.10086.cn`。
2. **巡检周期比滑动窗口长。** 默认巡检 1 小时，而移动窗口只有 30 分钟——即使写回了，两次巡检之间也会空掉。

### 采取的措施

**（1）抓取成功后写回续期后的 cookie**（`persistStorageState`）

`src/services/scraper_wallets.mjs` 新增该函数：抓取成功（或保活访问）后把浏览器上下文当前的 cookie 原子写回登录态文件（先写 `.tmp` 再 rename，并保留一份 `.bak`）。单平台路径与批量路径都已接入。

实测验证：抓取一次后 `chargeresource` 过期时间从 `15:29:03` 推到 `15:43:03`，正好是「访问时刻 + 30 分钟」。

**（2）给运营商加一条更快的保活节奏**（`startCarrierKeepAlive`）

`src/services/monitor.js` 新增保活器，与巡检并行运行：

- 每分钟检查一次，到期才访问网厅；
- 间隔取自 `CARRIER_KEEPALIVE_MS`：移动 10 分钟、电信 1 小时、联通 30 分钟（联通未联调，先取保守值）；
- 保活只做「访问 + 写回 cookie」，**不提取余额、不写余额历史、不触发充值单**——否则每 10 分钟写一条历史会污染数据并让阈值判断频繁触发；
- 会话已失效时（跳转登录页）主动推送手机提醒，比等 1 小时后的巡检报错更早，同一平台 6 小时内只推一次。

保活访问的是网厅入口页即可，不需要点菜单进余额子页。

**（3）不能靠纯 HTTP 续期**

实测用 `fetch` 带 cookie 直接 GET 网厅：移动返回 200 但 **Set-Cookie 条数为 0**（不触发续期）；电信返回 412（被拦截）。所以续期必须走真实浏览器，保活开销无法避免。

### 仍然需要重新登录的情况

| 情况 | 表现 |
|---|---|
| 运营商强制下线（如异地登录、长时间未活动） | 服务端直接失效，续期也救不回来，需重新登录 |
| 移动短信登录的随机码会话本身有服务端上限 | 长时间不访问仍可能被回收 |
| cookie 文件被删或损坏 | 保活会跳过（没有登录态文件），巡检报错并提示重新登录 |

登录态文件在 `src/wallet-states/`，已确认在 `.gitignore` 内（含新生成的 `.bak`），凭据不会进版本库。

### 3.7 电信那两枚 cookie（7 天 / 1 年）到底管什么

登录态文件里 189.cn 实际下发的是一对同名前缀的票据，在 `login.189.cn` 与 `www.189.cn` 各存一份，所以看起来是 4 条：

| `yiUIIlbdQT3fS` | login/www.189.cn | 1 年 | 滑到「访问时刻 + 1 年」 |

最初推测「一枚管短期会话、一枚管长期信任」，但这只是推测。用**裁剪对照实验**做了证伪（2026-11-20，判定口径统一用 `detectCarrierLoggedIn`：正文含「账户余额」且跟真实数字，或出现「退出登录」）：

| 变体（只改动 cookie 集合，其余不变） | 结果 |

| 删 `yiUIIlbdQT3fT`（7 天那枚） | 登录 ✓ |
| 两枚票据都删 | 登录 ✓ |
| 删 `EcsLoginToken` | 登录 ✓ |
| 删 `JSESSIONID-NEW-PROD` | 登录 ✓ |
| 删 `EcsCaptchaKey` | 登录 ✓ |
| 删 `_secure_gateway_v2_token_jxAeo079E` | **掉登录**（干净的未登录态：账户余额 `--`） |
| 删 `_user_location_auth_v2_profile` | 用户中心模块「内容加载失败」，余额区不渲染 |

结论与修正：

1. **决定登录态的不是那两枚票据。** 把 7 天和 1 年那两枚**全删掉，网页端照样登录**；反过来，只去掉 `_secure_gateway_v2_token_jxAeo079E`（会话 cookie，`expires=-1`）就立刻变成未登录态。
2. `_user_location_auth_v2_profile`（地区 / 用户档案）不决定登录，但决定**余额模块能否渲染**——少了它，用户中心报「内容加载失败」，余额取不到。
3. 那两枚票据的真实作用：服务端**每次访问都重新下发、并把有效期往后推**（7 天 / 1 年），属于网关侧的续期 / 信任票据，网页端不使用它们。它们在服务端的确切用途（跨端单点登录、设备信任等）**无法从客户端判定**，本文不作断言。

> **实验副作用（已发生，需知悉）**：裁剪实验会向 189.cn 发送**残缺凭证**，服务端据此把会话作废了——实验进行到中途时，连「完整登录态」变体也从登录变成未登录，用原始文件复核基线同样如此。**电信会话因此需要重新登录一次。**
> 教训：不要拿生产账号做凭证裁剪实验；若必须做，应使用测试账号。

### 3.8 无头化尝试结果，以及保活的弹窗策略

**能不能无头？——不能，四种组合全部空页面。**

| 启动组合（都带登录态） | 正文长度 |
|---|---|
| Playwright / 系统 Chrome `headless: true` | 0 字 |
| 系统 Chrome `--headless=new` | 0 字 |

结论：189.cn 拦的不是「无头」这个标志，而是**浏览器自动化特征本身**——连新无头模式（`--headless=new`）都拿不到正文。所以电信只能有头窗口抓，这是站点策略，改代码绕不过去。

**保活需不需要人工点击？——不需要。** 保活全程自动：开一个浏览器窗口 → 访问网厅首页 → 把续期后的 cookie 写回文件 → 关窗。中间不需要点任何按钮。

**弹窗能减吗？——能，原来多弹了一半。**

余额巡检本身就是每小时访问一次 189.cn 并写回 cookie，**7 天窗口已经被它续住**；再挂一个「每小时保活」属于纯冗余，而且每次都要多弹一次窗。因此把电信的单独保活从 1 小时放宽到 **12 小时**（保留为巡检被禁用/失败时的兜底）：

| | 改前 | 改后 |
|---|---|---|
| 电信每小时弹窗次数 | 2 次（巡检 1 + 保活 1） | **1 次**（仅巡检） |
| 单独保活间隔 | 1 小时 | 12 小时 |

**保活不再误报「续期成功」。** 实测发现两种「掉了但看不出来」的情况：

- 移动：服务端作废会话时下发 `ssoFail` cookie，**URL 仍停在首页**，只查 URL 会漏判；
- 电信：会话作废后**仍停在 `/web/`**，但首页已回到未登录态。

因此给规则加了两个开关：`sessionFailMarkers`（移动：查 `ssoFail` 标记）与 `sessionCheck: 'text'`（电信：用正文判定）。命中即判定会话失效，立即推送手机提醒，不再等下一次巡检。

### 3.9 移动的会话有硬上限，定期访问续不命（实测，2026-11-20 晚修正）

> **本节的时长发过两次修正，以 §3.13 的最终实测为准。**
> 最初观察到「约 30 分钟」；晚间用更严格的对照实验重新测量，真实上限是**登录后约 55~62 分钟**。
> 结论方向没变：**移动的会话有服务端硬上限，定期访问续不命**。

保活按 10 分钟一次连做多次都报「续期成功」，之后才跳 `login.10086.cn`；同期登录态文件里出现了服务端下发的 `ssoFail` 标记（过期时间正好是服务端下发时刻）。

即：**移动的会话寿命从「登录时刻」起算，定期访问续不命**。`chargeresource` 确实被续期了（过期时间每次被推到「访问时刻 + 30 分钟」），但真正决定会话的凭证不受它影响——对比 `.bak` 与当前文件可见每次访问后它的**值不变**，服务端并没有换发会话。

保活在移动上的价值因此不是「续命」，而是**第一时间发现失效并提醒用户重新登录**（原本要等 1 小时后的巡检才发现）。

### 3.10 同运营商的多个号码：登录态会不会互斥

**先说结论：运营商服务端不互斥，但我们本地原先会撞车（已修）。**

分两层看：

**服务端（运营商侧）：不同号码互不影响。** 网厅会话按账号维护，登录 A 号拿到的 cookie 与 B 号无关。实测登录态文件里能看出账号隔离——移动的 `sendflag` cookie 值里带账号标识（`11201548279`），电信的 `login.189.cn` localStorage `smsLoginHistory` 记录本次登录的号码（`19076243361`）。所以登第二个号码不会把第一个踢下线。

**本地（我们的实现）：原先会互相覆盖。** 原先登录态文件名只按运营商分：

```
中国移动话费 (carrier_cmcc) → storage_carrier_cmcc.json
移动副卡     (carrier_cmcc) → storage_carrier_cmcc.json   ← 同一个文件！
```

第二个号码登录时直接覆盖第一个的登录态文件，此后两个平台共用一份 cookie——其中一个平台抓到的余额可能是另一个号码的，且登录态失效会同时影响两个平台。

**修复：把「规则维度」和「登录态维度」拆开。**

| 维度 | 函数 | 规则 | 例子 |
|---|---|---|---|
| 网站 / 运营商 | `ruleKeyFor(name, provider)` | 同运营商所有号码**共享** | 移动主卡与副卡都用 `carrier_cmcc` 的标签组、正则、菜单入口 |
| 账号 | `storageKeyFor(name, provider, id)` | 每个号码**独立** | 移动副卡 → `carrier_cmcc_7` |

关键约束：**内置规范名沿用固定 key**（`中国移动话费` → `carrier_cmcc`），保证既有登录态文件继续可用、不用重新登录；只有自定义名平台（副卡等）才按 `provider + 平台 id` 派生唯一 key。

涉及改动的调用方（全部传入平台 id）：`balance.js` 的运营商抓取与 scrape 抓取、`monitor.js` 的保活、`routes.js` 的登录态查询与登录启动、`wallet-login.mjs` 的登录目标、`wallet-check.mjs` 的抓取验证。

顺带修掉两处会指错账号的地方：抓取失败的错误提示、保活失效的手机推送，现在都指向该平台自己的 key（`wallet-login.mjs carrier_cmcc_7`），而不是笼统的 provider。

**添加第二个号码的步骤：**

1. 在页面上新增平台：provider 选 `carrier_cmcc`（或 `carrier_ct` / `carrier_cu`），平台名自定义（如「移动副卡」），**余额查询 URL 可留空**（会自动用内置网厅入口）。
2. 点该平台的「登录」按钮，浏览器窗口里登录第二个号码。
3. 之后两个号码各自独立巡检、独立保活、独立告警。

回归测试：新增 6 项断言覆盖「规范名 key 不变」「同运营商第二号码 key 互不相同」「规则 key 按网站共享」。

### 3.11 页面上的两个倒计时：预计存活 / 续命

在平台名下方以小字显示两行倒计时（不新增表格列）：

```
中国移动话费
预计存活 29:16
续命 02:28
```

**两个倒计时的口径（需求对齐结论）：**

| 倒计时 | 含义 | 取值 |
|---|---|---|
| 预计存活 | 登录态过期倒计时 | 关键会话 cookie 的过期时间 |
| 续命 | 下一次访问网站续登录态的时间倒计时 | 保活与余额巡检中**较早**的那个 |

**为什么必须指定「关键会话 cookie」。** 登录态里混着当天就过期的 SDK cookie（189.cn 的 `sajssdk_2015_cross_new_user`）和 1 年期的长期 cookie，取「最早过期的那个」会得到假值——电信会显示 7 小时而不是 7 天。因此每个运营商显式声明用哪一枚：

| 运营商 | 声明 | 实测窗口 |
|---|---|---|
| 移动 | `{ exact: 'chargeresource' }` | 30 分钟 |
| 电信 | `{ suffix: 'T', siblingSuffix: 'S' }` | 7 天 |
| 联通 | `null`（未标定） | 联通未联调，显示「存活时间未标定」 |

电信那两枚票据的**前缀是随机的**（如 `yiUIIlbdQT3f`），不能硬编码全名——按「后缀 T 且存在同前缀 S 兄弟」识别。

**「续命」为什么取较早的那个。** 余额巡检本身每小时就访问一次网厅并写回续期后的 cookie，专门的保活只是兜底（电信 12 小时、移动 10 分钟）。所以实际下一次访问网厅的时刻 = min(保活到期, 巡检到期)。实测取到：

| 平台 | 预计存活 | 续命 | 续命来源 |
|---|---|---|---|
| 中国移动话费 | 29 分钟 | 约 3 分钟 | 保活（10 分钟节奏） |
| 中国移动话费2 | 30 分钟 | 约 7 分钟 | 保活 |
| 中国电信话费 | 7 天 | 约 60 分钟 | 巡检（1 小时节奏） |

**关键设计：观测状态优先于 cookie 过期时间。** 电信的 7 天票据未过期，但服务端可能已作废会话（实测：票据还在、页面已回未登录态 `账户余额 --`）。因此巡检与保活都会记录本次访问时**观测到的**会话状态（`session_alive_<id>`），观测到掉线时直接显示「未登录」，不再显示乐观估计的剩余时间。

**顺带修掉一处错误分类。** 电信会话作废后，首页仍带「账户余额」标签但值是 `--`，关键字会命中、余额提不出来，于是报成「页面中未找到余额」——把掉线伪装成页面结构异常。现在提取失败时（规则要求正文判定会话时）先检查正文里还有没有登录标识，报「未登录（页面已无登录标识，余额显示为占位符）」。

**实现要点：**

- 后端：`src/services/session_status.mjs` 纯函数（`pickKeySessionCookie` / `buildSessionStatus`），接口 `GET /api/carriers/session` 返回绝对时间戳。
- 前端：本地每秒走秒（不发请求），每 10 秒重新拉一次会话状态以拿到保活/巡检续期后的新时间戳。
- 状态取值：`ok` / `expired`（已过期，需重新登录）/ `not_logged_in`（未登录）/ `key_unknown`（登录态异常）/ `uncalibrated`（未标定）。

回归测试：新增 27 项断言（关键 cookie 识别、随机前缀、四种状态、续命取较早者、观测状态优先）。

### 3.12 登录态被写坏的事故：为什么「登录成功」不等于「登录态可用」

**事故经过（2026-11-20 下午实测）：**

| 时刻 | 事件 |
|---|---|
| 16:04:17 | 登录态文件完整（含网关 token + 档案 cookie，共 13 枚 cookie） |
| 16:42:35 | 巡检访问 189.cn → 服务端已不认这个会话，报「未登录（页面已无登录标识，余额显示为占位符）」 |
| 17:14:59 | 一次扫码登录「成功」，脚本把登录态文件覆盖写 → **只剩 11 枚 cookie，网关 token 与档案 cookie 双双消失** |
| 17:16:33 | 再次发起扫码登录，停在 `/web/` 首页空转 330 秒 |

**根因：登录判定刚成立时就保存，此时网厅还没下发关键 cookie。**

189.cn 的两枚关键 cookie 是在**用户中心 / 余额模块真正加载之后**才下发的：

- `_secure_gateway_v2_token*`（网关会话 cookie）——缺了服务端不认这个会话，首页回退成「账户余额 --」；
- `_user_location_auth_v2_profile*`（用户档案 cookie）——缺了用户中心报「内容加载失败」，余额区不渲染。

登录脚本原先的逻辑是「登录判定成立 → 立刻 `storageState()` 落盘」。但登录判定成立只说明**首页**显示了登录特征，此时这两枚 cookie 往往还没下发。落盘的就是一份**残缺登录态**：文件看起来有 11 枚 cookie、票据（`yiUIIlbdQT3fT` 等）也在，但少了决定会话的那两枚。

后果是双向的：既抓不到余额，也**把原本完整的登录态覆盖掉了**，且无法回退。

**还有一个结构性约束：189.cn 只能有一个登录态。**

项目侧发起扫码登录，会把服务端上其它会话挤掉（用户在日常 Chrome 里的 189.cn 登录态因此失效）。这是站点限制，不是 bug。**约定：189.cn 由项目独占，日常浏览器不再登录 189.cn。**

**修复（两层）：**

1. **登录保存前先预热**（`scripts/wallet-login.mjs` 的 `warmUpSession`）：登录判定成立后，主动访问网厅入口并点进余额 / 用户中心模块，等关键 cookie 下发齐全（最长 90 秒）才落盘；超时仍不齐则**不写文件**，并在日志里说明缺哪几枚。

2. **写回前做退化检查**（`src/services/scraper_wallets.mjs` 的 `persistStorageState`）：规则里显式声明 `sessionRequiredCookies`（电信：网关 token + 档案 cookie），写回时对比新旧 cookie 集——若新状态丢了旧状态已有的关键 cookie，**拒绝本次写回并保留原文件**。这样一次不完整的抓取就不会把完整登录态覆盖掉。

新增纯函数 `missingRequiredCookies` / `findDegradedCookies`（`src/services/session_status.mjs`），回归测试新增 10 项断言（完整 / 残缺识别、退化判定、旧状态本来就残缺不算退化）。

**顺带修掉一处误判：** 之前 `persistStorageState` 无条件覆盖写，即使抓取已经掉线也会把「掉线后的残缺 cookie 集」写进文件。现在退化检查会拦住这类写入。

### 3.13 「保活能延长存活」这个说法，两家网厅都不成立（2026-11-20 晚首测，2026-11-21 复核修正）

> **本节结论在 2026-11-21 被复核推翻过一次**，最终结论以 §3.14 为准。
> 首测（11-20）因为只看到「票据被换发」就下了「电信能续命」的结论，
> 11-21 等到实际死亡时刻才发现：票据换了，会话照样死。

**先纠正一个错误承诺。** 之前我说过「它们会自动访问来延长存活时间」——这个说法**对两家都不成立**。移动的会话有服务端硬上限；电信虽然每次访问都换发票据，但**换了也没换来更长的会话**。保活只能做到「尽早发现失效」，不能延长寿命。

#### 两家的机制（11-21 复核后的最终口径）

| | 移动 CMCC | 电信 CT |
|---|---|---|
| 访问后关键票据 | `chargeresource` **值不变**，只有过期时间被推到「访问时刻+30 分钟」 | `yiUIIlbdQT3fT` **值被换发**（票据确实换了） |
| 访问能否续命 | **不能** | **也不能**（11-21 复核：换了票据，25 分钟后照样死） |
| 会话窗口 | 登录后固定 ~60~66 分钟 | 登录后固定 ~60~80 分钟 |
| 原始告警 | 掉线即「跳转登录页」 | 掉线后仍停在 `/web/`，靠正文判定 |
| 189.cn/移动网厅无头 | 移动可无头 | 189.cn 拦无头（正文 0 字），保活必须有头窗口 |

判定依据：**对比 `.bak` 与当前文件的票据值**（移动值全同、只有过期时间在动；电信值确实变了），**加上实际死亡时刻**（11-21 三家在 02:52 还全通、03:10 全死）。

#### 掉线时间线（2026-11-20 晚实测）

| 时刻 | 事件 |
|---|---|
| 17:53 | 电信登录 |
| 17:57 | 移动登录 |
| 18:47:36 | 移动保活写入成功（票据续期到 19:17）——**会话此时还活着** |
| 18:53:38 | 巡检三家全通：电信 54.61 / 移动 70.9 / 副卡 21.9 |
| 18:56:57 | 下一轮巡检：移动主卡与副卡同时报「未登录（跳转登录页）」 |
| 19:54:18 | 电信也报「未登录（页面已无登录标识）」 |
| 21:02 / 21:03 / 21:05 | 三家重新登录 |
| 21:55:01 | 探针测三家**仍全部存活**（登录后 53 分钟） |
| 22:04 | 移动主卡已死（登录后 62 分钟） |

关键证据：**电信掉线点距上一次成功访问正好 ~60 分钟**（18:53 → 19:54），而当时的保活间隔被设成了 **12 小时**——远超窗口，等于必然掉线。

#### 排查过并排除的解释

- **不是「保活没跑」**：服务日志里保活一直在执行并报「会话续期成功」。
- **不是并发访问把自己顶了**：用副卡做对照实验（基线单次 → 两实例并发 → 并发后单次 → 等 30 秒 → 再单次），5 步全部存活。
- **不是无头访问触发了风控**：无头访问后立刻复测，会话当时仍然有效；且移动无头本就可用（189.cn 才是被拦的那个）。
- **不是用户在日常浏览器抢了会话**：Chrome 历史里 19:30 之后没有 189.cn / 10086.cn 访问记录。
- **不是「无人值守自动登录」可用**：曾一度以为存在免密自动登录（页面 21 秒就进入已登录态），**经用户确认那是本人扫码的结果**。随后三次真正的无人干预测试全部失败（每次 93 秒超时，页面显示「登录失败 请点击刷新」），**没有免密通道**。本次据此放弃了「自动重登」方案。

#### 修复

1. **「预计存活」不再用 cookie 票据寿命**（`src/services/session_status.mjs` + `src/services/session_meta.mjs`）
   之前电信显示 7 天（那是 `yiUIIlbdQT3fT` 票据的寿命），实际 60 分钟就死——这是假值。现在取「cookie 过期时间」与「会话窗口」里**更短**的那个，两家统一按「从登录时刻起算」（访问不刷新它）。会话窗口由规则里的 `sessionMaxAgeMs` 声明（两家均 60 分钟），起算点记在 sidecar 文件 `storage_*.json.meta.json`（登录脚本与服务共享；放 sidecar 而非数据库，因为两者是独立进程、各有 sql.js 内存库，同时写同一个 db 文件会互相覆盖）。

2. **电信保活间隔 12 小时 → 25 分钟（11-21 再调为 20 分钟）**（`CARRIER_KEEPALIVE_MS`）
   间隔必须小于会话窗口，否则连「尽早发现失效」都做不到（原先 12 小时 = 必然掉线）。
   代价是 189.cn 拦无头，保活需要有头窗口、会弹窗——这是提前预警的必要代价。
   同时 `renewCarrierSession` 对电信改为**走完整抓取路径**（点进余额模块）而不是只访问入口页：
   实测能换发票据的是完整抓取那次。这个开关现在独立为 `keepaliveFullScrape`，
   不再挂在 `sessionRenewable` 上（否则该标记变 false 后保活会退化成只访问入口页）。

3. **失效前主动预警**（`src/services/monitor.js`）
   移动这类「保活救不回来」的运营商，在会话窗口耗尽前 20 分钟就提醒重新登录（同一个登录周期只提醒一次），而不是等界面上变成「未登录」才事后知道。前端新增 `expiring` 状态（橙色「即将失效，请重新登录」）。

4. **告警不再谎报已送达**（`src/services/push.js` + `monitor.js`）
   `config.json` 里 `notify.serverchan` / `notify.bark` **都是空的**，但日志一直无条件打印「已推送登录态失效提醒」——一条也没真正发出去。这是「用户最后才知道全挂了」的直接原因。现在 `sendPhoneNotify` 返回 `delivered`，未配置通道时日志明确写「**没有推送出去**」并提示改用界面上的「登录」按钮。

5. **登录时记录绑定号码**（`scripts/wallet-login.mjs`）
   登录成功后从正文解析脱敏号码（如 `178****6402`）写入 meta 文件并在页面显示。用途：副卡若被登成主卡号，余额会串号，而页面上看不出绑定的是哪个号。

回归测试：`scripts/test-carrier-balance.mjs` 新增 27 项断言（会话寿命标定、可续命标记、两种起算口径、`expiring` 状态、meta 读写、脱敏号码解析），并把一条**基于错误前提**的旧断言替换掉：

- 旧断言「电信保活间隔不短于 1 小时」的前提是「电信会话窗口有 7 天」——那是从票据寿命推出的假值。
- 新断言改为「保活间隔 < 实测会话窗口」「不短于 10 分钟」「留 2 倍以上余量」。

最终：运营商测试 141 项全通过，`npm test` 37 项全通过。

#### 仍然存在的限制

- **移动仍需约每小时重新扫码一次**。实测没有免密登录通道，而会话硬上限无法用访问绕过。这是站点限制，不是实现缺陷。若要真正免人工，只能换思路（例如改用运营商能力开放平台，但那需要企业资质，见 §2.3）。
- **电信保活每 20 分钟弹一次有头窗口**。189.cn 拦无头，无法回避；窗口出现约几秒后自动关闭。
- **`sessionMaxAgeMs` 是实测标定值**，两家网厅若调整策略需重新标定。

### 3.14 复核：三家又一起死了（2026-11-21）

#### 现象

用户反馈三家又同时变成「未登录」。上一节的结论是「电信能靠访问续命、移动不能」，**本次复核推翻了它的一半**。

#### 时间线（服务日志 + 余额历史 + cookie 差异三路对齐）

| 时刻 | 事件 | 来源 |
|---|---|---|
| 11-20 21:09 / 21:10 | 三家登录（余额历史各有一条） | balance_history |
| 11-20 22:15 | 巡检三家全错 | 服务日志 |
| 11-21 02:09 / 02:12 | 用户重新扫码后，三家又抓到余额（21.9 / 75.9 / 54.61） | balance_history |
| 11-21 02:52 | 服务重启后首轮巡检：三家全通 | 服务日志 |
| 11-21 03:00 ~ 03:01 | 保活三家都报「会话续期成功」 | 服务日志 |
| 11-21 03:10 前后 | 三家全死 | 服务日志 |
| 11-21 03:26 | 电信也报「页面已无登录标识」 | 服务日志 |

#### 决定性证据：访问**不能**延长会话

对比 `.bak`（02:52 巡检写回）与当前文件（03:00 保活写回）的逐 cookie 差异：

- **移动**：`chargeresource` 的**值完全相同**（指纹 `c2ebd1160c`），只有过期时间被推到「访问时刻+30 分钟」。
  服务端从未换发会话 → 定期访问只是让 cookie 看起来还新鲜。
- **电信**：`yiUIIlbdQT3fT@www.189.cn` 的**值确实变了**（`aC7OqCsQ…` → `aisaQJNZ…`，过期 02:52 → 03:01）。
  票据换了，**但会话照样在 03:26 死**——若访问真能续命，应该活到 04:01。

⇒ **「访问能续命」对两家都不成立。** 上一节写「电信能」是因为只看到了票据换发，没等到死亡时刻。

另一条独立证据：把当前**已失效**的登录态拿去跑保活，移动两家都正确报「跳转登录页」——**保活的失效判定本身没坏**，它如实报告了死亡。

#### 三家为什么「同时」死

不是巧合也不是批量作废，而是**同一次登录的三个账号**，寿命都从各自登录时刻起算 ~60 分钟。三家是先后扫码的（02:09 / 02:12），所以死亡时刻也就接近（03:10 / 03:26）。

#### 排除过的解释

- **不是保活没跑**：日志显示保活每轮都在跑。
- **不是并发访问自顶**：副卡 5 步对照实验（基线 → 两实例并发 → 并发后单次 → 等 30 秒 → 再单次）全部存活。
- **不是我们在写回时写坏登录态**：`.bak` 与当前文件的 cookie 差异只有过期时间，无一丢失。
- **不是无头触发风控**：无头访问后立即复测会话仍有效。
- **不是日常 Chrome 抢会话**：Chrome 历史今天无 10086.cn / 189.cn 访问（最后一条是昨天 17:15）；9222 调试端口也未开启。
- **不是没有免密登录**：经用户确认，之前那几次「20 秒自动登录成功」是**他本人扫码**的结果；三次真正的无人干预测试全部 93 秒超时。

#### 顺带查出的真缺陷：预警压根没触发过

三个 `storage_*.json.meta.json` 的 `loggedInAt` **全是 null**——用户这次重新登录**没有走我们的登录脚本**（用的是自己的浏览器），所以脚本没记录到登录时刻。后果：

- 「预计存活」倒计时算不出锚点 → 界面上的时间不准。
- 「窗口耗尽前 20 分钟预警」依赖 `loggedInAt` → **预警从未触发**，用户只能等界面变成「未登录」才知道。

#### 本次修复

1. **撤销「电信能续命」的结论**（`src/services/scraper_wallets.mjs`）
   两家 `sessionRenewable` 统一为 `false`；会话窗口统一 60 分钟、都从登录时刻起算。
   电信保活改走完整抓取路径的开关独立为 `keepaliveFullScrape`（否则标记变 false 后保活会退化成只访问入口页）。
   电信保活间隔 25 → 20 分钟（目的是**尽早发现**，不是续命）。

2. **保活日志不再说谎**（`src/services/monitor.js`）
   「会话续期成功」→「访问成功（会话仍有效；注意：访问不会延长该网厅的会话寿命）」。

3. **倒计时锚点支持「用户自行扫码」**（`src/services/session_meta.mjs` + `session_status.mjs` + `routes.js`）
   meta 新增 `deadAt` / `aliveSince`：会话从失效恢复为有效的那一刻就是新会话的起点。
   `buildSessionStatus` 新增 `revivedAt` 入参：`loggedInAt` 缺失时用 `aliveSince` 兜底
   （它必然晚于真实登录时刻 → 估算**偏保守**，对「提前预警」是安全方向）。
   预警逻辑同样改用这个兜底锚点。

4. **前端文案改成「下次检查」**（`public/index.html`）
   原先的「续命 N」会被误读成「到点访问就能续上」。现在明确写成「下次检查 N」，
   悬停提示写清“访问续不回来；此处是下次检查失效的时刻”。

回归测试：`scripts/test-carrier-balance.mjs` 152 项全通过（新增 10 项：锚点兜底、`deadAt`/`aliveSince`、
两家都不可续命、`keepaliveFullScrape` 独立开关），`npm test` 48 项全通过。

### 3.15 重新登录后仍显示「未登录」：会话状态只由巡检写入（2026-11-21）

#### 现象

用户在 13:09~13:12 重新登录三家后，**余额能抓到，界面却仍显示「未登录」**——两者自相矛盾。

实测（修复前）：

- `POST /api/platforms/5/refresh` → `{"ok":true,"balance":75.9}`
- `POST /api/platforms/6/refresh` → `{"ok":true,"balance":54.61}`
- `POST /api/platforms/7/refresh` → `{"ok":true,"balance":21.9}`
- 但 `GET /api/carriers/session` → 三家全是 `state: "not_logged_in"`

#### 根因

会话状态存在数据库设置 `session_alive_<id>` 里，而**只有巡检（`monitor.js`）和保活会写它**。
手动刷新走的路径（`routes.js` → `refreshPlatformBalance`）完全不写这个字段。

于是：巡检在用户登录**之前**跑过一轮，报了「未登录」→ 写入 `session_alive_5 = 0`。
用户随后重新登录、手动刷新成功抓到余额，但**没有任何一条路径把这个 0 翻回 1**，
状态就永久钉在「未登录」。

数据库现场印证（修复前）：`session_alive_5=1`、`session_alive_7=1`（被随后的保活翻回来了）、
`session_alive_6=0`（电信保活间隔 20 分钟，尚未轮到）——**谁最后写谁说了算，与实际登录态无关**。

#### 修复

1. **写入点收敛到唯一共同入口**（`src/services/balance.js`）
   `refreshPlatformBalance` 是手动刷新、巡检、到账后重查三条路径的**唯一共同所有者**，
   会话观测改在这里记录 → 三条路径自动一致，判定口径只有一份。

2. **判定改为三态**（`src/services/session_status.mjs`）
   新增 `classifySessionObservation`：
   - `alive`（抓到余额）→ 写 1
   - `dead`（跳登录页）→ 写 0
   - `unknown`（网络抖动、页面结构变化等与登录态无关的失败）→ **保留上一次观测值**

   旧巡检实现是 `r.ok ? 1 : (dead ? 0 : 1)`——**任何失败都记成会话有效**，
   网络抖动会掩盖真正的掉线。新实现区分三态，不让无关失败污染会话状态。

3. **删掉 monitor 里的重复写入**（`src/services/monitor.js`）
   巡检不再自己写 `session_alive_*`，避免出现两套口径不同的实现。

4. **meta 补记**（`src/services/balance.js`）
   `alive` 时补 `markSessionAlive`（桌面 Chrome CDP 回退路径原先不记，
   导致「用户在自己浏览器登录」时没有倒计时锚点）；`dead` 时补 `markSessionDead`
   （抓取失败路径原先不标失效，meta 里留着旧的「上次有效访问时刻」，
   倒计时继续给乐观估计）。

#### 验证（实测，非推断）

- 修复前：三家手动刷新全部成功 → 接口仍报三家 `not_logged_in`
- 修复后（服务带新代码重启）：
  - 移动两家：启动巡检后自动翻回 `state: "ok"`，倒计时 27~28 分钟
  - 电信：手动刷新后翻回 `state: "ok"`，倒计时 53 分钟
  - 三家 `anchorSource` 均为 `login`（登录时刻已正确记录：13:09 / 13:12 / 13:10）
- `scripts/test-carrier-balance.mjs` → **158 项全通过**（新增 6 项：三态判定）
- `npm test` → **48 项全通过**

### 3.16 会话掉了却查不到「什么时候掉的」：补上落盘日志与失效时刻记录（2026-11-21 16:37）

#### 起因

用户报告「登录又掉了」，并问「多久掉的」。查下来的结论是：**服务一直正常跑，
判定也完全正确，但没人能回答这个问题**。

#### 关键发现：坏的不是判定，是提醒送不出去

拉出服务后台日志后，时间线完整了（此前只能靠文件时间戳反推）：

| 时刻 | 事件 | 来源 |
|---|---|---|
| 13:19:15 | 巡检：三家全部成功 | 服务日志 |
| 13:19~13:57 | 保活连续 8 次报「访问成功（会话仍有效）」 | 服务日志 |
| ~13:57 | 移动两家报「登录态将在约 12 分钟后失效」 | 服务日志 |
| **约 14:08** | 保活报「会话已失效（服务端下发会话失效标记 ssoFail）」 | 服务日志 |
| 14:19:42 | 巡检：三家全错 | 服务日志 |
| 15:19:43 | 巡检：三家全错 | 服务日志 |
| 16:19:42 | 巡检：三家全错 | 服务日志 |
| **16:37** | **用户来问「多久掉的」** | 对话 |

⇒ **系统 14:08 就知道会话死了，判定完全正确**；用户 16:37 才发现，
是因为提醒只写进了控制台日志，手机上一条也没收到（推送通道没配）。
所以本次改造的重点不是改判定，而是**让「什么时候掉的」可查、让提醒能送到**。

同时查出一处**日志谎报**：日志里写着 `[monitor] 已推送登录态过期提醒: 中国电信话费`，
而 `sendPhoneNotify` 的返回值是 `delivered:false`——通道没配，什么都没发。
同一条消息在保活分支里是如实报告的（「没有推送出去」），巡检分支却无条件打印「已推送」。

#### 本次修复

1. **服务日志落盘**（新建 `src/services/logger.js`）
   此前所有日志只进控制台，进程一退出就什么都没留下——这正是「查不到什么时候掉的」的根因。
   现在按天写 `logs/server-YYYY-MM-DD.log`，同步追加（进程被杀也不丢）。
   - 长 token 自动打码（cookie 值、票据都是这种形态，不能写进日志文件）
   - 文件带 UTF-8 BOM：Windows 自带的 PowerShell 5.1 与记事本默认按 ANSI(GBK)
     读无 BOM 的 UTF-8 文件，中文会显示成乱码（实测确认过：内容对，显示乱）
   - 目录跟着 `LLM_MANAGER_DATA_DIR` 走，冒烟测试的隔离实例不会把测试输出混进真实日志

2. **会话元信息记录「首次失效时刻」**（`src/services/session_meta.mjs`）
   `deadAt` 早先是「最近一次确认失效的时刻」，每次观测都覆盖——这就是为什么
   只能查到 16:27 而不是 14:08。现在：
   - `deadAt` = **首次**确认失效的时刻（不再被覆盖）
   - `lastDeadAt` = 最近一次确认失效的时刻
   - `deadReason` = 失效原因（跳转登录页 / 服务端失效标记 / 页面已无登录标识）
   - 重新登录时这些字段清空（新会话周期）

3. **保活状态独立记录**（新增 `markSessionKeepalive`）
   早先 `markSessionDead` 一并写 `keepaliveState='dead'`，于是**巡检刷新失败**
   （也走 `markSessionDead`）会把 `keepaliveAt` 刷成刷新时刻——界面显示
   「保活判定失效」，而实际上保活根本没判定过失效，是巡检先发现的。
   现在保活字段由保活链路**独占**写入，与抓取链路互不干扰。
   界面因此能区分四种状态：保活正常 / 保活判定失效 / 保活异常 / 保活尚未运行。

4. **失效提醒按登录周期节流**（`src/services/monitor.js`）
   原先按「6 小时内只推一次」节流，但会话实际每约 60 分钟就死一次、
   用户重新登录后再死——6 小时内的后续失效全被吞掉。
   改用「平台 id + 登录时刻」做键：同一次登录只提醒一次，重新登录后自动可以再提醒。
   同时修掉巡检分支的谎报（按 `res.delivered` 如实报告）。

5. **登录成功后立刻抓一次余额**（`src/routes.js` + `scripts/wallet-login.mjs`）
   此前登录脚本存好登录态就结束，界面上的余额还是上一次巡检留下的旧数；
   而巡检周期（1 小时）与会话寿命（约 60 分钟）一样长，很容易整个撞在会话刚失效的窗口里，
   用户看到的是「抓取失败」而不是新余额。
   现在登录脚本退出后服务端立刻对该平台跑一次余额抓取，「登录」与「余额更新」合成一个动作。

6. **保活顺带取余额，金额变了才写历史**（`src/services/scraper_wallets.mjs` + `src/services/balance.js`）
   保活本来就在访问网厅，顺手把余额读出来几乎不花额外代价。
   - 金额**变了**才写 `balance_history`（否则每 10 分钟一条同金额记录，会把变化曲线刷花）
   - 无论变没变都更新「最后查询」时刻——保活确实访问了网厅、确实读到了余额，
     这是一次真实的余额查询。余额的新鲜度不再取决于巡检是否恰好撞在会话还活着的那个小时里

7. **错峰重登**（`src/services/session_status.mjs` 新增 `planStaggeredRelogin`）
   三家是先后扫码的，寿命都从各自登录时刻起算，失效时刻只差几分钟，会连着掉。
   现在按失效先后排序，并给每家一个**错开的建议重登时刻**（相邻至少间隔 20 分钟），
   界面显示「第 N 个重登 · 建议 HH:MM」。新增「🕐 按顺序重登」按钮，
   按建议顺序逐个弹窗口，扫完一个自动弹下一个。

## 6. 已知限制与后续项

- **移动已联调，电信与联通未联调**：移动的入口、登录方式、余额文案、提取结果均已用真实页面确认（抓取值 70.9 与页面一致）。电信与联通仍需你本人完成一次网厅登录后才能确认余额页文案；若某家抓不到，按 §7 的方式调规则即可。
- **同一页面存在多个金额，取错会误报欠费**：移动个人中心页同时有「可用余额 70.90元」与「账户总余额 0.00元」。若误取后者，会把 0 当成欠费并错误触发充值单。已为此实现排除词机制（`exclude`）：标签含「账户总/总额/累计/预存/冻结/赠费」的金额一律不采信；且关键字兜底路径要求关键字与数字之间只允许分隔符，不允许夹杂其他中文标签。两条都有回归用例覆盖。
- **电信需要桌面 Chrome**：实测 189.cn 对无头浏览器做站点级拦截（页面正文 0 字）。电信的自动抓取依赖 `scripts/start-chrome-debug.cmd` 启动的桌面 Chrome 调试模式；无头失败时代码会自动回退到 CDP 模式重试，两者都不可用时请改用手动录入。
- **依赖登录态**：登录态过期（运营商通常几天到几周）会导致抓取失败。系统已有连续 3 次失败推手机提醒的机制，但重新登录仍需你本人操作。
- **联通的余额在二级菜单**：首页没有余额链接，需要先展开「查询」再点二级入口，规则已按此顺序配置，但仍可能因省份版本差异而失效。
- **运营商风控**：频繁访问网厅可能触发验证码或限流。巡检频率为每小时一次，属正常用户量级，但异常时会失败并记录错误，不会静默返回 0。
- **只取话费余额**：当前只提取金额，流量余量与短信余量未提取（页面上标签与格式差异更大，且阈值告警语义不同）。需要时可在 `CARRIER_RULES` 里加 `dataKey` 字段扩展。
- **余额单位为元**：电信官方接口返回的是「分」，本项目抓取路径读的是页面展示的元，未做单位换算。
- **回退路径**：任何一家运营商抓取不稳，把该平台的 `balance_type` 改成 `manual`，用页面「录入余额」按钮手工录入，阈值告警照常工作。
